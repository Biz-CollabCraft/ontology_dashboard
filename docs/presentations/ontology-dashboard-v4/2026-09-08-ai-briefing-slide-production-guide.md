# AI 브리핑 발표 슬라이드 제작 문서 v2

2026-09-08 · 병합된 demo `ab63cfe9`의 구현과 검증을 반영한 7장 제작 기준이다. 발화 대본은 [개인 발표 대본](ontology-dashboard-v4-5min-script.md)을 따른다. 원래 대본·제작 문서는 historical/에 보존했다. 이 문서는 실제 PPT 파일의 수정 완료를 뜻하지 않는다.

## 발표 구성

기존 7장 순서를 유지한다. 한 장에 하나의 주장을 두고, 세 기여는 문제 인식 → 가정 → 해결 → 검증으로 설명한다. 서버 기반 AI 브리핑, 근거 패키지, ViewModel/화면, 검증된 AI 브리핑으로 기여를 표현한다. 상태 변경과 승인·정비 실행의 소유권은 담당 시스템과 사람에게 남긴다.

| 장 | 화면 제목 | 슬라이드 내용 | 근거와 주의점 |
|---|---|---|---|
| 1 | 예측 결과만으로는 정비 시점을 정하기 어렵습니다 | 예측 결과·점검 기록·작업요청·생산 조건이 분리된 문제 | 정비 효과나 운영 개선을 이미 측정한 것처럼 말하지 않는다 |
| 2 | 판단 근거와 미확인 조건을 한 화면에 제공합니다 | 최종 CNC 브리핑 캡처. 예측 → 점검 → 승인 기록 → 착수 전 확인 | 보관된 입력·응답을 재검증하는 로컬 시연 |
| 3 | 근거 구성, 생성·제공, 출력 검증을 나눠 설계했습니다 | 근거 패키지와 시간 정합성 / AI 브리핑 워크플로우 / 브리핑 생성·검증 흐름 | Closed-loop 전체를 개인 기여로 포함하지 않는다 |
| 4 | 같은 설비와 기준 시각의 근거만 전달합니다 | 관계 연결 → 근거 선별 → ViewModel. 이후 시각·다른 설비 기록은 현재 판단에서 제외 | 근거·시간·화면 전달 계약 **32/32** |
| 5 | 생성과 조회를 분리하고 유효한 저장본만 제공합니다 | watcher 또는 명시적 생성 → 검사 → 저장 → 조회. 유효 저장본 없으면 준비 중 | 워크플로우 상태 전이·경계 계약 **24/24** |
| 6 | 내용 검사 통과 후보 반환율이 60.0%p 높았습니다 | **20.8% → 80.8%, +60.0%p**를 크게 표시. 선호 **17/24, 70.8%**는 보조 | 기존 Luna A/B 각 120회. 에이전트 선호이며 사람 평가 아님 |
| 7 | 입력 계약과 실제 화면의 오류 대응을 각각 확인했습니다 | 입력→화면 준비 **40/40**, 화면 조합 **24/24**, 오류 대응 **16/16**을 별도 표기 | 로컬 통합·팀 DB 읽기 확인. 운영 전체 연결·배포·현장 사용자 평가는 미검증 |

## 2장 화면

[최종 화면 캡처](../../ui/assets/final-briefing/engineering-ready.png)를 사용한다. 브리핑과 오른쪽의 승인 기록·미확인 조건이 함께 보이도록 배치한다. 원래 기록 시각을 최근 기록으로 바꾸지 않는다.

발표자가 가리킬 부분은 세 곳이다.

1. SOP 기준 초과가 무엇을 점검해야 하는지로 이어지는 문장.
2. 점검 결과와 승인 기록을 설명하는 문장.
3. 착수·완료·재고·작업 가능 시간의 미확인 조건과 마지막 판단 키워드.

내부 필드명·근거 번호·원시 단위는 슬라이드에 추가하지 않는다. 점진적 문장 표시는 검증 후 공개 효과다. 실제 토큰 스트리밍이나 버튼마다 새 모델 생성이라고 설명하지 않는다.

## 5장 생성·조회 경계

일반 조회는 생성하지 않는다. watcher 및 권한이 있는 명시적 브리핑 생성·다시 생성 요청은 생성 경로로 들어간다. 재생성이 유예되더라도 과거 문장 재사용이 자동 허용되지 않으며, 현재 근거와 정확히 일치하고 검증된 저장본이 있어야 제공한다.

최종 시연의 ‘브리핑 검증’ 버튼은 보관된 응답을 현재 검사기로 확인하는 별도 replay 경로다. 제품 생성 경로와 같은 버튼으로 그리지 않는다. 원격 strict schema 응답만으로 검사가 끝나는 도식도 피한다.

## 6장 성과 해석

| 지표 | 수치 | 조건 |
|---|---|---|
| 내용 검사 통과 후보 반환율 | Direct 25/120 → 생성·검증 97/120 | 같은 8개 입력 × 각 15회, 기존 gpt-5.6-luna 산출물, 공통 검사 |
| 블라인드 에이전트 선호 | 17/24, 70.8% | 에이전트 3개 × 8사례, 현장 사용자 평가 아님 |
| 판단 유용성 자동평가 | 0/120 → 18/120 | 보수적 자동평가, 부록만 사용 |

원시 모델 응답 정확도, 현장 업무 성공률, 운영 비용 절감으로 이름을 바꾸지 않는다. 기존 평가와 최신 v3.4 점검을 하나의 평가로 합치지 않는다.

## 7장 및 부록 검증 범위

| 표시 위치 | 결과 | 무엇을 확인했는가 |
|---|---|---|
| 본문 | 40/40 | 8개 입력 × 5개 전달 계약 |
| 본문 | 24/24 | 8개 입력 × 3개 관점의 실제 브라우저 replay |
| 본문 | 16/16 | 연속 클릭·지연·손상 응답·재시도·화면 너비 |
| 발표자 노트 | 별도 24/24 및 실패 차단 | 실제 로컬 예측 → 검사 → 워크플로우 → 임시 SQLite → 제품 조회 API → 화면. 외부 LLM은 통제 응답 |
| 발표자 노트 | 416 passed, 2 skipped, 2 warnings | PostgreSQL 포함 원격 서버 회귀. 다른 필수 원격 검사 2개도 성공 |
| 발표자 노트 | 100대 × 3회 동일 | 팀 DB의 동일 읽기 전용 트랜잭션에서 기준 시각 이하 최신 기록 |
| 발표자 노트 | 최초 0/2 → 최종 2/2 | 최신 v3.4 실제 LLM 호출. 각각 피드백 1회로 수정 후 통과 |

같은 24/24라도 워크플로우 계약·replay 화면·전체 연결 화면은 다른 검사다. 이 수치들을 합산한 종합 정확도를 만들지 않는다.

## 한계 표현

사용할 문장: “로컬 예측과 임시 DB를 잇는 화면 경로, 팀 DB 읽기, 실제 LLM 호출을 각각 확인했습니다. 운영 DB부터 실제 LLM과 배포 화면까지의 전체 연결과 현장 사용자 효과는 아직 검증하지 않았습니다.”

팀 DB는 합성 운영 문맥을 포함하고, 조회 범위의 저장 AI 요약은 없다. DB 쓰기 자체를 전혀 검증하지 않았다는 설명도 부정확하다. 임시 SQLite와 격리 PostgreSQL 검증은 수행했으며 공유 팀 DB는 읽기 전용으로 점검했다.
