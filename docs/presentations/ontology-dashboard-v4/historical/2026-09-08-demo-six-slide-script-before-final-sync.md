# Ontology Dashboard — v4 5분 발표 대본
현재 HTML 1~6장 시각화에 맞춘 대본. 목표 발화 4분 50초 + 화면 전환 여유 10초. 실제 길이는 리허설로 조정한다.

## 1장. 문제 정의 — 15초 (0:00–0:15)

위험을 예측해도 정비 시점은 바로 정해지지 않습니다. 위험 근거와 현장 점검 결과, 부품 준비와 예상 정지시간을 함께 봐야 하기 때문입니다.

## 2장. 결과 화면과 담당 범위 — 35초 (0:15–0:50)

공기압축기의 정비를 검토하는 상황입니다. 왼쪽의 예측 결과, 점검·정비 이력, 부품과 정지시간 정보를 연결해 오른쪽 브리핑으로 제공합니다.

이 브리핑에서는 어떤 부품을 교체해야 하는지, 기존 작업에 어디까지 포함됐는지, 부품과 정지시간 조건은 어떤지를 함께 확인할 수 있습니다.

저는 이 근거를 구성하고 AI 요약을 생성·검증·저장해 화면에 제공하는 백엔드를 구현했습니다. 근거 구성, AI 생성·제공, 시간 정합성과 실패 처리의 세 부분으로 설명하겠습니다.

## 3장. 온톨로지 기반 근거 구성 — 60초 (0:50–1:50)

먼저 온톨로지는 설비·조치·부품·기록이 어떤 관계인지 명시한 구조입니다. 앞 장의 세 입력 정보가 가운데 관계도로 이어집니다.

화면별로 데이터를 조회해 붙일 수도 있지만, 같은 설비의 정보라도 현재 조치와 관련 있는지 구분해야 합니다. 그래서 관계를 명시하고 출처와 시점을 함께 보존했습니다. 여기서는 공기압축기의 교체 조치와 필요한 부품, 점검·정비 기록을 연결합니다. 현재 관측 시각과 22일 전 정비 기록도 구분합니다.

연결한 정보를 모두 전달하지 않고, 역할과 판단에 맞춰 AI에 전달할 근거 후보를 선별했습니다. 별도 합성 운영 맥락 평가에서는 후보 29개 중 8개를 전달해 후보 수가 72.4퍼센트 줄었습니다. 평가에서 지정한 필수 근거와 제한사항은 모두 보존했습니다.

이렇게 구성한 근거가 다음 장의 AI 워크플로우로 들어갑니다.

## 4장. AI 생성·제공 워크플로우 — 80초 (1:50–3:10)

이 그림은 백엔드가 요약을 준비하고, 사용자가 화면을 여는 순서입니다.

아래 줄의 watcher가 새 근거를 주기적으로 확인하면 근거를 구성하고 선별합니다. 이어서 AI 요약을 생성·검증한 뒤 저장합니다. 같은 근거와 조건의 저장본이 있으면 위쪽 경로로 재사용합니다. 사용자가 화면을 열 때는 저장된 결과를 조회하고, 아직 준비되지 않았다면 대기 상태를 반환합니다.

아래 두 평가는 별도로 진행했습니다. 왼쪽은 대표 8개 사례를 15회씩 실행한 로컬 LLM 반복 평가입니다. 120회 모두 출력 검증을 통과했고 기본 요약 전환은 없었습니다.

오른쪽은 최종 제공 결과의 품질 비교입니다. 원천 필드를 넣은 방식은 38.7점, 구성된 근거를 넣은 방식은 79.7점, 복구와 재사용을 적용한 방식은 100점이었습니다. 필수 사실과 역할별 항목, 금지 주장을 기준으로 채점했습니다.

마지막 방식은 생성에 실패했을 때 기본 요약으로 복구하고 그 결과를 재사용해 평가 항목을 충족했습니다. 기본 요약 8회와 저장본 재사용 16회가 포함됩니다. 다음 장에서 이 실패 대응을 설명하겠습니다.

## 5장. 시간 정합성·실패 처리 — 70초 (3:10–4:20)

왼쪽부터 근거를 확인하고 AI 요약을 생성한 뒤 출력과 시점을 검사해 저장하는 흐름입니다.

AI 호출이 실패하거나 출력 검증을 통과하지 못하면 아래의 기본 요약 경로로 이동합니다. 기본 요약은 정해진 규칙으로 구성한 근거 기반 요약입니다. 이 결과도 검증하고, 전환 상태와 사유를 기록합니다.

근거 A로 시작했는데 처리 중 새 근거 B가 확인되면, 이전 결과를 차단하고 최신 근거를 재조회하는 경로로 연결합니다. 로컬 시점 불일치 주입에서 32건 모두 탐지·차단했고, 별도 재조회 경로에서는 8건 모두 복구했습니다.

아래는 서비스 예외가 발생했을 때 처리 실행을 다시 시도하는 정책입니다. 최초 시도를 포함해 기본 최대 두 번까지 시도하고, 한도에 도달하면 실패를 반환합니다. 앞서 설명한 AI 호출 실패의 기본 요약 전환과는 적용 지점이 다릅니다.

여러 실패 유형을 합한 별도 로컬 실패 주입 검증도 총 24건을 통과했습니다.

## 6장. 화면으로 회수와 결론 — 30초 (4:20–4:50)

처음의 AI 브리핑 화면으로 돌아오겠습니다. 정비 시점을 검토할 때 필요한 근거와 실행 조건이 이 화면에 모입니다.

저는 근거 구성부터 AI 요약의 생성·검증·저장·조회까지 이어지는 백엔드 흐름과, 시간 정합성·실패 처리를 설계하고 검증했습니다. AI는 근거를 설명하고, 영향 판단과 협의·승인은 사람이 담당합니다.

## 발표자 참고 — 대본 밖에 보관

- 화면 카드는 사용자 제공 캡처 값을 재구성한 자료이며 원천 JSON 캡처가 아니다.
- 72.4%는 합성 맥락의 후보 개수 감소율이다. 토큰·비용 감소율이나 사용자 유용성이 아니다. 필수 항목은 평가에서 지정한 범위다.
- 120회 반복 평가와 방식별 24회 파이프라인 비교는 독립 평가다. 골드 100점은 LLM 단독 성능이나 현장 효과를 뜻하지 않는다.
- 32/32, 8/8, 24/24는 기존 로컬 평가 기록이며 이번 슬라이드 수정으로 새로 실행한 결과가 아니다.
- 최대 2회 시도는 최초 시도를 포함한다. fallback은 provider/출력 실패, 실행 재시도는 서비스 예외에 대한 정책이다.
- 타임라인은 정책을 설명하는 그림이다. 모든 분기의 실제 함수 호출 순서를 그대로 복제한 실행 추적도는 아니다.
- 승인·상태 변경은 AI의 역할이 아니다. 생산 대응 실행·협의 전용 상태 머신·별도 Queue/알림은 발표 범위에 포함하지 않는다.
