## 1. 제작 결론

이번 발표는 “LLM을 붙였다”가 아니라, 서버가 예측 결과를 기준으로 운영 기록을 묶고, 그 근거를 ViewModel과 화면에 전달한 뒤, AI 브리핑 생성 결과를 검증해서 제공한 작업으로 설명한다.

듣는 사람이 가장 먼저 이해해야 할 문장은 다음이다.

> 예측 결과만으로는 정비 판단이 어렵기 때문에, 서버에서 예측 결과의 기준 시각에 맞는 운영 근거를 묶고, 검증된 AI 브리핑으로 화면에 제공했습니다.

슬라이드에는 `Product Result Artifact`, `snapshot_basis`, `LLM pipeline` 같은 내부 용어를 크게 쓰지 않는다. 화면과 대본에서는 아래 표현을 사용한다.

| 내부 구현 용어 | 발표 표현 |
|---|---|
| Product Result Artifact | 예측 결과 |
| snapshot_basis.observed_at | 예측 결과 기준 시각 |
| evidence package | 근거 패키지 |
| AssetDetailViewModel | ViewModel 또는 화면 전달 모델 |
| LLM pipeline | 브리핑 생성·검증 흐름 |
| backend | 서버 |

`스냅샷`이라는 단어를 꼭 써야 할 때는 대본에서만 “코드상 snapshot_basis로 관리되는 기준 시각” 정도로 설명한다. 슬라이드 본문에서는 `기준 시각`이 더 낫다.

### 발표에서 조심해야 할 수치

`64.17% → 78.33%`, `+14.16%p`, `0.82` 같은 점수성 수치는 본문 큰 숫자로 쓰지 않는다. 질문을 부를 가능성이 크고, 발표의 중심 메시지와도 덜 맞다. 필요하면 발표자 노트나 부록에만 둔다.

비용은 측정하지 않았다. “비용이 낮아졌다”라고 말하지 않는다. “불필요한 호출을 줄이기 위한 구조를 비교했다”, “비용 효율적인 운영 가능성을 검토했다” 정도로 말한다.

현장 판단 유용성, 사용자 만족도, 다운타임 감소, 운영 KPI 개선은 측정하지 않았다. 발표에서는 fixture, live-provider, 에이전트 예비 검수 범위로 제한한다.

## 3. 전체 스토리

이 발표의 흐름은 기능 나열이 아니라 다음 이야기로 가야 한다.

1. 예측 결과는 나왔지만, 그것만으로 정비 판단은 어렵다.
2. 이유는 센서 예측, 점검 결과, 작업요청, 승인 상태, 정비 이력, 생산 영향이 서로 다른 기록에 흩어져 있기 때문이다.
3. 그래서 서버에서 예측 결과 기준 시각을 고정하고, 그 기준에 맞는 근거만 묶었다.
4. 묶은 근거는 ViewModel을 통해 화면 문장과 상태 카드로 전달했다.
5. AI는 이 근거를 바탕으로 브리핑 문장을 만들지만, 서버가 출력 스키마와 금지 표현을 검증한다.
6. 검증을 통과하지 못하면 재작성하거나 거절한다.
7. 이 구조는 fixture 기반 검증에서는 입력부터 화면 표현 준비까지 안정적으로 통과했다.
8. 실제 현장 사용자 평가와 운영 성과 검증은 다음 단계로 남긴다.

발표 감정선은 “복잡했지만 완성했다”다. 다만 감정으로 주장하지 말고, 화면 매핑과 검증 수치로 보여준다.

## 4. 추천 슬라이드 구조

4분 발표라면 8장이 가장 듣기 쉽다. 7장으로 줄이면 5장과 6장이 다시 과밀해진다. 꼭 7장이어야 하면 6장과 7장을 합친다.

### 1장. 문제 정의

목적: 프로젝트 문제와 내 역할을 한 번에 잡는다.

화면 구성:

- 제목: `예측 결과만으로는 정비 판단이 끝나지 않습니다`
- 왼쪽: 예측 결과
- 가운데: 판단에 필요한 운영 기록들
- 오른쪽: 담당자 확인

슬라이드 문구:

```text
안녕하세요. 서버 기반 AI 브리핑 기능을 맡은 유호범입니다.
이 프로젝트는 이상감지 예측 결과를 정비 판단에 필요한 근거로 연결하는 문제에서 출발했습니다.
```

대본 핵심:

> 예측 결과가 있어도 점검 결과, 작업요청, 승인 상태, 부품 조건, 생산 영향을 함께 봐야 조치 여부를 판단할 수 있습니다. 저는 이 흐름에서 서버가 근거를 묶고, AI 브리핑을 생성·검증해 화면에 제공하는 부분을 맡았습니다.

금지:

- “AI가 정비 시점을 판단했다”라고 말하지 않는다.
- “운영 효율을 개선했다”라고 말하지 않는다.

### 2장. 결과 화면

목적: 최종 화면을 먼저 보여주고, 이후 슬라이드의 기준점을 만든다.

화면 구성:

- 실제 데모 화면 캡쳐를 크게 넣는다.
- 전체 화면보다 AI 브리핑 카드와 근거 요약이 읽히는 crop을 사용한다.
- 왼쪽에는 사용자가 읽는 흐름을 짧게 둔다.

권장 흐름 라벨:

```text
예측 결과
점검 결과
작업요청 승인
착수 조건 확인
```

슬라이드 하단 문구:

```text
화면에는 내부 코드와 원시 근거 번호를 크게 드러내지 않고, 담당자가 읽을 수 있는 문장으로 제공합니다.
```

대본 핵심:

> 이 화면이 최종 제공 형태입니다. 예측 결과에 점검 결과와 승인된 작업요청을 연결하고, 아직 확인되지 않은 착수 조건은 확정하지 않고 남겨둡니다. 이후 장에서는 이 한 화면 뒤에 있는 서버 구조를 설명드리겠습니다.

### 3장. 세 가지 설계 축

목적: 전체 구조를 한 장에서 보여준다.

화면 구성:

```text
예측 결과
  ↓
근거 패키지·시간 정합성
  ↓
AI 브리핑 워크플로우
  ↓
브리핑 생성·검증 흐름
  ↓
화면 제공
```

슬라이드 문구:

```text
서버 제공 흐름을 세 가지 설계 축으로 나눴습니다.
```

반드시 유지할 대본:

> 저는 이 문제를 세 부분으로 나눠 설계했습니다. 첫째, 서버가 예측 결과와 그 기준 시각을 출발점으로 삼고, 그 기준에 맞는 운영 데이터를 근거 패키지로 만든 뒤 ViewModel을 통해 화면에서 브리핑과 근거 상태를 함께 볼 수 있게 제공했습니다. 둘째, watcher 기반 AI 브리핑 워크플로우로 생성과 조회를 분리하고, 유효한 저장본이 없으면 준비 중 상태를 반환하도록 했습니다. 셋째, LLM이 만든 브리핑은 서버에서 관계 흐름, 출력 스키마, 금지 표현을 검증한 뒤 재작성하거나 거절하도록 했습니다.

### 4장. 근거 패키지와 시간 정합성

목적: 온톨로지/관계 모델이 왜 필요한지 화면에 연결한다.

문제 인식:

예측 결과의 기준 시각과 다른 설비, 다른 이벤트, 기준 이후 기록이 섞이면 현재 판단 근거처럼 보일 수 있다.

가정:

서버가 LLM 입력 전에 기준 시각, 설비, 이벤트, 제외 조건을 확정해야 한다.

해결:

설비와 작업, 생산 정보의 관계를 명시하는 읽기 전용 관계 모델을 두고, 같은 설비와 같은 이벤트의 기록만 근거 패키지에 포함한다. 기준 이후 기록, 다른 설비 기록, 근거 없는 재고·납기·완료 상태는 제외한다.

검증:

필수 근거 보존, 부적합 근거 제외, 기준 시각 유지, ViewModel 전달 계약을 확인한다.

수치:

```text
근거 패키지·시간 정합성·ViewModel 전달 계약 32/32 통과
```

시각화:

```text
예측 결과 기준 시각
  ↓
같은 설비
같은 이벤트
기준 시각 이전 기록
  ↓
근거 패키지
```

온톨로지 질문 대비:

> 단순히 데이터를 붙이는 것보다, 설비와 작업, 생산 정보의 관계를 명시해야 어떤 기록이 왜 판단 근거인지 설명할 수 있었습니다. 다만 확장성은 온톨로지라는 이름 자체보다, 근거 선별 규칙을 도메인별 어댑터로 분리한 점에서 설명하는 게 정확합니다.

### 5장. 화면 문장과 근거 매핑

목적: 듣는 사람이 “그래서 화면 문장이 어떤 근거에서 나왔는데?”를 바로 이해하게 한다.

이 장은 새로 만드는 것이 좋다. 기존 구조도보다 화면 매핑이 더 중요하다.

화면 구성:

왼쪽: 실제 화면의 브리핑 문장 하나를 크게 보여준다.

```text
현재 커플링 편심이 기록되고 관련 작업요청이 승인된 상태지만,
실행 여부가 확인되지 않아 현장 확인 결과를 이어 판단할 단계입니다.
```

오른쪽: 이 문장을 만든 근거와 제외한 근거를 나눠 보여준다.

사용한 근거:

```text
예측 결과: 커플링 편심
점검 결과: 편심 확인, 정비 권고
작업요청: 승인됨
기준 시각: 예측 결과 기준 시각
```

확정하지 않은 항목:

```text
착수 여부 미확인
완료 여부 미확인
재고 수량 미확인
실제 생산 손실 미확인
```

검증 수치:

```text
입력→화면 제공 안정성 40/40 통과
```

대본 핵심:

> 이 장에서는 화면 문장 하나를 근거와 매핑해 보겠습니다. 브리핑은 승인 상태를 말할 수 있지만, 착수나 완료가 확인되지 않으면 확정하지 않습니다. 재고와 실제 생산 손실도 근거가 없으면 말하지 않습니다. 이 구분이 서버 검증과 ViewModel 전달의 핵심입니다.

### 6장. AI 브리핑 워크플로우

목적: 왜 생성과 조회를 분리했는지 설명한다.

문제 인식:

운영 기록은 갱신될 수 있고, LLM 호출은 지연과 비용이 있다. 매 조회마다 생성하거나, 오래된 저장본을 그대로 주면 문제가 생긴다.

가정:

사용자 화면은 빠르게 읽혀야 하고, 생성은 서버가 검증 가능한 시점에 처리해야 한다.

해결:

watcher가 새 근거를 확인한다. 생성과 조회를 분리한다. 생성 결과는 검증 후 저장한다. 화면은 저장본을 조회한다. 유효한 저장본이 없으면 준비 중 상태를 반환한다. 명시적 새로고침은 최신 근거 재확인으로 처리한다.

검증:

watcher 감지, 생성/조회 분리, 저장본 재사용, 준비 중 반환, 기준 시각 변경 시 stale 브리핑 차단, 실패 사유 기록을 확인한다.

수치:

```text
AI 브리핑 워크플로우 상태 전이 계약 24/24 통과
```

표현 주의:

- “새로고침이 생성 요청이다”라고 말하지 않는다.
- “사용자 호출로 선택했다”라고 말하지 않는다.
- “비용이 낮아졌다”라고 말하지 않는다.
- “비용 효율적인 구조를 비교했다”라고 말한다.

### 7장. 브리핑 생성·검증 흐름

목적: Pipeline의 기여와 평가 수치를 보여준다.

문제 인식:

LLM에 근거를 그대로 넣으면 내부 코드, 원시 단위, 근거 없는 운영 주장, AI가 결정하는 듯한 문장이 나올 수 있다.

가정:

LLM은 자연어 표현을 만들 수 있지만, 사실과 경계 검증은 서버가 맡아야 한다.

해결:

서버가 관계 흐름을 입력에 포함한다.

```text
이상 신호
점검 대상
점검 결과
작업요청/승인
실행 공백
```

LLM이 브리핑을 만들면 서버가 출력 스키마, 계약, 금지 표현을 검사한다. 실패하면 재작성하거나 거절한다.

검증:

Direct LLM과 Pipeline을 같은 8개 fixture, 120회 조건으로 비교한다.

메인 수치:

```text
내용 검사 통과 후보 반환율
Direct 20.8% → Pipeline 80.8%
+60.0%p
```

보조 수치:

```text
블라인드 에이전트 예비 선호율
Pipeline 17/24, 70.8%
```

대본 핵심:

> 여기서 중요한 점은 LLM 출력 자체를 성과로 본 것이 아니라, 서버가 통과시킨 후보만 화면에 제공했다는 점입니다. 같은 fixture 120회 비교에서 내용 검사 통과 후보 반환율은 Direct 20.8%에서 Pipeline 80.8%로 올라갔습니다. 다만 이 수치는 fixture 기반 내용 검사이고, 실제 현장 사용자 평가가 아닙니다.

### 8장. 안정성 평가와 한계

목적: 과장 없이 마무리한다.

화면 구성:

```text
예측 결과
근거 패키지
AI 브리핑
ViewModel
화면
```

중앙 수치:

```text
입력→화면 제공 안정성 40/40 통과
```

검증 범위:

```text
8개 fixture × 5개 계약
입력 해시
기준 시각
선택 근거
ViewModel 전달
화면 표현 준비
```

한계:

```text
fixture 기반 live-provider 평가
실제 DB 쓰기 없음
배포 검증 없음
운영 상태 변경 없음
현장 사용자 평가는 별도 필요
운영 KPI로 확대 해석하지 않음
```

마무리 대본:

> 정리하면 저는 예측 결과를 바로 조치로 연결한 것이 아니라, 서버에서 기준 시각에 맞는 근거를 묶고, ViewModel을 통해 화면에 제공하며, AI 브리핑 결과를 검증하는 흐름을 만들었습니다. 이번 검증은 fixture 기반이므로 현장 효과로 확대하지 않습니다. 다음 단계는 실제 화면 사용 로그와 담당자 피드백을 기준으로 평가하는 것입니다.

## 5. 7장으로 줄여야 할 때

반드시 7장이어야 하면 다음처럼 합친다.

| 8장 구조 | 7장 압축 |
|---|---|
| 1 문제 정의 | 유지 |
| 2 결과 화면 | 유지 |
| 3 세 가지 설계 축 | 유지 |
| 4 근거 패키지와 시간 정합성 | 유지 |
| 5 화면 문장과 근거 매핑 | 유지 |
| 6 AI 브리핑 워크플로우 | 유지 |
| 7 브리핑 생성·검증 흐름 | 7장 앞부분 |
| 8 안정성 평가와 한계 | 7장 뒷부분 |

하지만 7장 압축은 마지막 장이 과밀해진다. 발표 시간이 4분이어도 8장으로 나누고 장당 25~35초로 말하는 편이 듣기 쉽다.

## 6. 슬라이드 제작 프롬프트

아래 프롬프트를 다음 제작 단계에서 사용한다.

```text
현재 발표 자료를 4분 발표용으로 다시 제작해줘. 핵심은 “LLM을 붙였다”가 아니라, 서버가 예측 결과의 기준 시각에 맞춰 운영 근거를 묶고, ViewModel을 통해 화면에 제공하며, AI 브리핑 생성 결과를 검증해 통과 후보만 제공한 작업으로 보여주는 것이다.

슬라이드는 8장으로 구성한다.

1. 문제 정의: 예측 결과만으로는 정비 판단이 끝나지 않는다.
2. 결과 화면: 실제 데모 화면을 크게 보여주고, 예측 결과 → 점검 결과 → 작업요청 승인 → 착수 조건 확인 흐름을 표시한다.
3. 세 가지 설계 축: 근거 패키지·시간 정합성, AI 브리핑 워크플로우, 브리핑 생성·검증 흐름을 서버 제공 흐름으로 보여준다.
4. 근거 패키지와 시간 정합성: 예측 결과 기준 시각, 같은 설비, 같은 이벤트, 기준 시각 이전 기록만 포함하는 구조를 보여준다. 수치는 32/32 통과.
5. 화면 문장과 근거 매핑: 실제 브리핑 문장 하나를 왼쪽에 두고, 오른쪽에 사용한 근거와 확정하지 않은 항목을 나눠 보여준다. 수치는 입력→화면 제공 안정성 40/40 통과.
6. AI 브리핑 워크플로우: watcher, 생성/조회 분리, 저장본 재사용, 준비 중 상태, 명시적 새로고침은 최신 근거 재확인이라는 흐름을 보여준다. 수치는 24/24 통과.
7. 브리핑 생성·검증 흐름: 이상 신호 → 점검 대상 → 점검 결과 → 작업요청/승인 → 실행 공백의 관계 흐름을 LLM 입력에 포함하고, 출력 스키마와 금지 표현을 서버가 검증해 재작성/거절하는 구조를 보여준다. 메인 수치는 Direct 20.8% → Pipeline 80.8%, +60.0%p. 보조 수치는 블라인드 에이전트 선호율 17/24, 70.8%.
8. 안정성 평가와 한계: 예측 결과부터 근거 패키지, AI 브리핑, ViewModel, 화면까지 40/40 통과를 보여주고, fixture 기반 평가이며 실제 DB 쓰기, 배포, 운영 상태 변경, 현장 사용자 평가는 없었다고 명시한다.

표현 기준:
- “백엔드”보다 “서버”라고 쓴다.
- “Product Result Artifact”보다 “예측 결과”라고 쓴다.
- “snapshot”보다 “기준 시각”이라고 쓴다.
- “LLM 파이프라인”보다 “브리핑 생성·검증 흐름”이라고 쓴다.
- “AI가 결정했다”, “AI가 승인했다”, “AI가 정비를 실행했다”처럼 책임 주체가 AI로 보이는 표현은 쓰지 않는다.
- “현장 판단 유용성 향상”, “운영 효율 개선”, “다운타임 감소”처럼 측정하지 않은 성과 표현은 쓰지 않는다.
- 수치는 fixture, live-provider, 에이전트 예비 검수 범위를 반드시 함께 표시한다.
```

## 7. 예상 질문 답변

### AI sensor fusion과 뭐가 다른가

센서 fusion은 여러 센서 신호를 합쳐 상태를 추정하는 작업에 가깝다. 이 발표의 작업은 예측 결과 이후에 점검 결과, 작업요청, 승인 상태, 생산 영향 같은 운영 기록을 연결해 화면에서 판단 근거로 읽히게 만드는 서버 구조다.

### 왜 온톨로지 또는 관계 모델을 썼나

같은 설비의 데이터를 모으는 것만으로는 부족했다. 공기압축기가 어떤 설비에 공기를 공급하는지, 점검 결과가 어떤 작업요청과 연결되는지 알아야 화면 문장이 판단 근거가 된다. 그래서 설비와 작업, 생산 정보의 관계를 명시하는 관계 모델을 사용했다.

### 온톨로지를 추가하면 확장성이 보장되는가

그렇게 말하면 근거가 약하다. 확장성은 온톨로지라는 용어보다, 근거 선별 규칙을 도메인별 어댑터로 분리한 구조에서 설명한다. 새로운 도메인은 관계와 선별 규칙을 어댑터로 추가하는 방식이 더 안전한 설명이다.

### Alert만 주면 되지 않나

Alert는 위험 신호를 알려주는 데 초점이 있다. 실제 조치 여부는 점검 결과, 작업요청, 승인 상태, 착수 조건, 생산 영향까지 함께 봐야 한다. 그래서 이 작업은 alert를 최종 판단으로 만들기보다, 사람이 확인할 수 있는 근거 기반 브리핑으로 제공한다.

### 실시간 갱신이면 LLM 비용이 커지지 않나

그 문제가 있어서 생성과 조회를 분리했다. 운영 데이터가 갱신될 수 있는 상황에서 매번 LLM을 호출하지 않고, 새 근거를 watcher가 확인한 뒤 검증된 저장본을 제공한다. 유효한 저장본이 없으면 준비 중 상태를 반환한다. 비용 자체는 측정하지 않았으므로 비용 절감이라고 말하지 않는다.

## 8. 최종 제작 체크리스트

- [ ] 2장 화면 캡쳐가 실제 데모 화면 기준인지 확인한다.
- [ ] 화면 문장과 근거 매핑 장을 추가한다.
- [ ] 각 기여 장에 문제 인식, 가정, 해결, 검증, 수치가 모두 들어간다.
- [ ] `Product Result Artifact`, `snapshot_basis`, `fixture` 같은 내부 용어가 본문 큰 텍스트에 드러나지 않는다.
- [ ] 수치 옆에 범위를 붙인다.
- [ ] 한계는 마지막에 몰아넣지 말고 관련 수치 바로 뒤에도 짧게 붙인다.
- [ ] 최종 판단과 승인은 담당자가 수행한다고 마무리한다.
