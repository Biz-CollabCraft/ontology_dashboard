# 개인 발표 대본 · 도식 중심 7장

2026-09-08 최종 demo 동기화. 목표 4~5분이며 실제 길이는 리허설로 확인한다. 기존 7장 흐름과 문제 인식 → 가정 → 해결 → 검증 순서를 유지한다. 본문은 발화 대본이며 참고 항목은 발화하지 않는다.

## 1장. 문제 정의

안녕하세요. 저는 서버에서 운영 데이터를 근거 패키지로 만들고, AI 브리핑을 생성·조회·검증해 화면에 제공하는 기능을 맡은 유호범입니다.

이 프로젝트의 출발점은 이상감지 예측 결과만으로는 정비 시점을 판단하기 어렵다는 점이었습니다. 점검 결과와 작업요청, 승인 상태, 정비 이력처럼 판단에 필요한 기록이 서로 다른 곳에 있기 때문입니다.

이 기록을 그대로 LLM에 넣으면 근거 누락, 관계 단절, 내부 코드 노출, 근거 없는 운영 주장 같은 문제가 생길 수 있습니다. 그래서 저는 서버가 먼저 근거를 확정하고, 생성과 조회를 분리한 뒤, LLM 출력까지 검증하는 구조로 접근했습니다.

## 2장. 결과 화면

2장입니다. 이 화면은 최종 브리핑 화면입니다.

CNC 가공기의 예측 결과를 점검 결과와 승인된 작업요청까지 연결하고, 착수 전에 확인해야 할 조건을 같은 화면에서 이어서 보여줍니다.

화면에서는 내부 코드, 근거 번호, 원시 단위가 그대로 드러나지 않게 했습니다. 보는 사람은 보전이나 운영 담당자이고, AI가 결정을 내리는 화면이 아니라 근거와 상태를 확인하는 화면입니다.

## 3장. 세 가지 설계 축

3장입니다. 저는 이 문제를 세 부분으로 나눠 설계했습니다. 첫째, 서버가 예측 결과와 그 기준 시각을 출발점으로 삼고, 그 기준에 맞는 운영 데이터를 근거 패키지로 만든 뒤 ViewModel을 통해 화면에서 브리핑과 근거 상태를 함께 볼 수 있게 제공했습니다. 둘째, watcher 기반 AI 브리핑 워크플로우로 생성과 조회를 분리하고, 유효한 저장본이 없으면 준비 중 상태를 반환하도록 했습니다. 셋째, LLM이 만든 브리핑은 서버에서 관계 흐름, 출력 스키마, 금지 표현을 검증한 뒤 재작성하거나 거절하도록 했습니다.

다음 장부터는 각 축을 문제 인식, 가정, 해결, 검증, 수치 순서로 설명드리겠습니다.

## 4장. 근거 패키지와 시간 정합성

4장입니다. 첫 번째 기여는 근거 패키지와 시간 정합성입니다.

문제 인식은 예측 결과가 기준 시각을 갖고 있는데, 여기에 다른 시점이나 다른 설비 기록이 섞이면 현재 근거처럼 보일 수 있다는 점이었습니다. 가정은 서버가 LLM 입력 전에 기준 시각과 근거 범위, 제외 조건을 확정해야 한다는 것입니다.

그래서 설비와 작업, 생산 정보의 관계를 명시하는 읽기 전용 관계 모델을 두고, 예측 결과의 기준 시각에 맞는 같은 설비와 같은 이벤트의 기록만 근거 패키지에 포함했습니다. 기준 이후 기록, 다른 설비 기록, 근거 없는 재고와 납기, 완료 상태는 제외했습니다.

검증은 필수 근거 보존, 부적합 근거 제외, 기준 시각 유지, ViewModel 전달 계약을 확인하는 방식입니다. 수치는 근거 패키지·시간 정합성·ViewModel 전달 계약 32/32 통과입니다. 과거 근거 선별 예시는 29개 후보에서 8개로 줄인 사례입니다.

## 5장. AI 브리핑 워크플로우

5장입니다. 두 번째 기여는 AI 브리핑 워크플로우입니다.

문제 인식은 스냅샷이 갱신될 때마다 LLM을 무조건 호출하면 비용과 대기 시간이 커지고, 반대로 저장본을 아무렇게나 재사용하면 오래된 브리핑이 화면에 나갈 수 있다는 점이었습니다. 가정은 생성과 조회를 분리해야 한다는 것입니다.

해결은 watcher 기반 흐름입니다. watcher가 새 근거를 확인하면 서버가 브리핑을 생성하고 검증해 저장합니다. 화면은 유효한 저장본을 조회하고, 없으면 준비 중 상태를 반환합니다. 일반 조회는 생성하지 않습니다. 권한이 있는 사용자의 브리핑 생성·다시 생성 요청은 별도 생성 경로로 처리합니다.

검증은 watcher 감지, 생성과 조회 분리, 저장본 재사용, 준비 중 반환, 오래된 브리핑 차단, 실패 사유 기록을 상태 전이로 확인했습니다. 워크플로우 상태 전이와 경계 계약은 24/24 통과했습니다.

## 6장. 브리핑 생성·검증 흐름

6장입니다. 세 번째 기여는 브리핑 생성·검증 흐름입니다.

문제 인식은 LLM이 브리핑을 만들 때 근거에 없는 완료 상태나 내부 코드를 문장에 섞을 수 있다는 점이었습니다. 가정은 LLM은 설명을 만들고, 사실과 계약 검사는 서버가 맡아야 한다는 것입니다.

그래서 서버가 이상 신호, 점검 대상, 점검 결과, 작업요청과 승인, 실행 공백의 관계 흐름을 입력에 포함했습니다. LLM이 브리핑을 만들면 서버가 출력 스키마와 금지 표현을 검사하고, 실패하면 재작성하거나 거절합니다.

검증은 두 가지로 봤습니다. 먼저 같은 8개 예시 입력을 각 방식에서 15회씩 평가한 기존 Luna 산출물에서 Direct 방식의 내용 검사 통과 후보 반환율은 20.8퍼센트였고, 서버 검증 흐름을 거친 브리핑 생성·검증 방식은 80.8퍼센트였습니다. 차이는 60.0퍼센트포인트입니다. 추가로 Direct와 Pipeline 출력을 라벨 없이 비교한 블라인드 에이전트 예비 검수에서는 브리핑 생성·검증 방식이 24표 중 17표, 70.8퍼센트에서 선호됐습니다. 다만 이는 현장 사용자 평가가 아니라 출력 품질을 보기 위한 보조 평가입니다.

## 7장. 입력부터 화면 제공까지의 안정성 평가와 한계

7장입니다. 마지막은 입력부터 화면 제공까지의 안정성 평가와 한계입니다.

여기서는 브리핑 자연어의 선호가 아니라, 예측 결과부터 근거 패키지, AI 브리핑, ViewModel, 화면까지 연결되는 전달 흐름이 깨지지 않는지를 확인했습니다. 예측 결과의 기준 시각이 근거 패키지와 ViewModel 전달까지 유지되는지도 포함했습니다.

입력 재현성, 기준 시각, 선택 근거, 화면 전달 모델과 화면 표현 준비를 확인해 40개 계약이 모두 통과했습니다. 실제 브라우저에서도 8개 입력과 3개 관점의 24개 조합을 확인했고, 연결 실패와 재시도 등 16개 오류 대응도 통과했습니다.

전체 연결 검사는 로컬 예측과 임시 DB를 사용했고, 팀 DB는 읽기 전용으로 확인했습니다. 실제 LLM 호출은 별도로 점검했습니다. 운영 DB부터 실제 LLM과 배포 화면까지 이어지는 전체 경로와 현장 사용자 효과는 아직 검증하지 않았습니다. 최종 판단과 승인은 담당자가 수행합니다. 감사합니다.

## 발표자 참고 — 발화하지 않음

- 발표 화면은 보관된 입력·응답의 재검증이다. 버튼을 누를 때 실시간으로 새 LLM 응답을 생성하는 시연이라고 설명하지 않는다. 점진적 표시는 검증 완료 문장을 보여주는 효과다.
- 제품의 일반 조회(GET), 권한이 있는 생성·다시 생성(POST), 데모의 보관 응답 재검증은 서로 다른 경로다.
- 32/32는 근거·시간·ViewModel 계약, 24/24는 워크플로우 계약, 40/40은 입력→화면 준비 계약이다. 실제 브라우저 24/24와 숫자가 같아도 같은 검사가 아니다.
- 브라우저 replay 24/24 외에 실제 규칙 기반 예측 → 워크플로우 → 임시 SQLite → 제품 조회 API → 화면 24/24 및 실패 차단을 별도로 확인했다. 이 전체 연결 검사는 외부 LLM 전송을 통제 응답으로 대체했다.
- Direct 25/120 (20.8%) → 브리핑 생성·검증 97/120 (80.8%), +60.0%p는 기존 v3.3 산출물의 공통 내용 검사 결과다. 최신 v3.4 신규 A/B나 현장 정확도로 말하지 않는다.
- 블라인드 선호 17/24 (70.8%)는 에이전트 3개 × 사례 8개 평가다. 현장 사용자 평가가 아니다.
- 최신 v3.4 실제 gpt-5.6-luna 호출은 최초 0/2 → 각 1회 재생성 후 최종 2/2. 신규 문장 6역할의 포맷터 검사도 통과했다. 작은 호출 점검이며 120회 성과에 합산하지 않는다.
- 원격 서버 회귀는 416 passed, 2 skipped, 2 warnings. 계약 벡터·예측 입력 통합 검사도 성공했고 PR #168은 병합됐다. 숫자는 회귀 범위이며 AI 품질 지표가 아니다.
- 팀 DB의 기준 시각 이하 최신 기록은 100대 × 3회 조회에서 동일했다. 전체 테이블에는 미래 관측이 있고 운영 문맥은 합성 데모 데이터다. 조회 범위의 저장 AI 요약은 없었다.
- 임시 DB 저장·조회는 검증했다. 공유 팀 DB는 읽기 전용으로 확인했으며 운영 상태를 변경하지 않았다. 운영 전체 연결, 배포, 현장 판단 유용성·사용자 만족도·운영 KPI·비용 절감은 미검증이다.
- 과거 120/120, 38.7→79.7→81.7, 64.2%→78.3%는 이 발표의 최신 성과로 사용하지 않는다. 역사적 대본은 historical/에 보존한다.
