# AI Solution Engineer 최종 발표 슬라이드 제작 명세

- 목적: Ontology Dashboard 프로젝트에서 수행한 Backend / AI Integration / Evaluation 기여를 AI Solution Engineer 직무 관점으로 설명한다.
- 결과물: 16:9(1920×1080) 단일 HTML 발표자료
- 분량: 본편 8장 + 부록 2장
- 기준: 구현한 것, 검증한 것, 향후 평가할 것을 시각적으로 구분한다.

## 1. 발표의 중심 주장

### 프로젝트 문제

복잡하게 연결된 제조 데이터를 조직이 빠르게 판단할 수 있는 근거로 전환한다.

### 내가 맡은 문제

서로 다른 시점과 출처의 데이터를 같은 판단 시점의 근거로 구성하고, 사람이 맥락을 파악할 수 있는 역할별 문장으로 안정적으로 변환한다.

### 직무 포지셔닝

요구사항을 운영 의사결정 문제로 해석하고, AI와 미리 정한 로직의 경계를 설계하며, Backend/API/데이터 계약으로 구현하고 실패 시나리오와 비교 평가로 검증한 AI Solution Engineer.

### 한 문장 메시지

> AI가 판단을 대신하는 것이 아니라, 판단에 필요한 복잡한 근거를 읽을 수 있는 문맥으로 변환한다.

### 구현 범위

- Backend 판단 지원 파이프라인
- 운영 근거 패킷과 기준시각 계약
- 읽기 전용 운영 도메인 조회
- 역할별 AI 요약
- 출력 검증, 제한된 재시도, fallback, 장애 격리
- 로컬 합성 시나리오 평가 하네스

### 범위 밖

- 예측 모델 자체 개발
- AI의 WorkOrder 생성, 승인, 상태 변경
- 실제 MES/CMMS/WMS/QMS 연동 효과
- 실제 비용 절감 및 운영 KPI 개선
- LLM 품질 우위에 대한 미검증 주장

**목적**
프로젝트 전체 문제와 내가 맡은 문제를 한 화면에서 분리한다.

**레이아웃**

- 상단 30%: 문제정의
- 하단 70%: 중앙 가로 흐름도
- 두 번째 단계인 `운영 근거`를 파란색으로 가장 강조

**상단 문구**

### 3쪽. 내가 정의한 설계 경계

**목적**
기술 목록이 아니라, 어떤 실패를 막기 위해 어떤 경계를 선택했는지 보여준다.

**레이아웃**

- 상단 65%: 3열 설계 기준 카드
- 하단 35%: 책임분리 흐름

| 기준 | 막으려는 실패 | 설계 선택 |
|---|---|---|
| 시간 정합성 | 예측은 10시, 재고는 어제 | 기준시각·출처·버전 고정 |
| 책임분리 | AI가 작업을 생성 | 읽기 전용 AI, 실행 권한 분리 |
| 확장성 | 품질 추가 시 전체 구조 변경 | 도메인 어댑터·표준 근거 블록 |

**하단 흐름**

`미리 정한 로직: 조회·검증·권한` → `AI: 근거 설명·역할별 요약` → `사람: 판단·승인·실행`

**하단 메시지**

`AI가 판단을 대신하지 않고, 판단 가능한 문맥을 만든다.`

### 4쪽. 운영 판단 지원 구현 흐름

**목적**
설계가 실제 Backend/AI 파이프라인으로 구현됐음을 보여준다.

**레이아웃**

- 본문 중앙: 5단계 가로 파이프라인
- 각 단계 아래: 구현 계약·컴포넌트 라벨
- 최하단: 권한 경계선

| 단계 | 시각 요소 | 구현 라벨 |
|---|---|---|
| 예측 결과 | 게이지 | `asset · risk · observed_at` |
| 근거 스냅샷 | 자물쇠 | `source · version · as_of` |
| 운영 관계 조회 | 눈 | `read-only tools` |
| 선택지 영향 구성 | 비교표 | `미리 정한 조립 로직` |
| 역할별 AI 요약 | 문서 | `structured AI output` |

**책임 영역 표시**

- 1~4단계 상단: 회색 띠 `미리 정한 로직`
- 5단계 상단: 파란 띠 `LLM`
- 최하단 빨간 경계: `WorkOrder 생성 · 상태 변경 · 승인 — 범위 밖`

**레이아웃**

- 좌측 58%: 설비 중심 관계 지도

**좌측 관계 지도**

- 중앙: 설비 A-17
- 주변: 생산오더, 재공품, 정비 가능 시간, 부품 재고, 기술자, 품질 로트, 납기 약속

- 점선: 누락 또는 미연결
- 빨간 테두리: 판단 제약
- 관계 라벨: 현재 작업, 진행 물량, 정지 가능, 수리 가능, 작업 가능, 검사 상태, 출하 영향

**우측 확장 구조**

`도메인 조회 어댑터` → `표준 근거 블록` → `운영 판단 패킷` → `역할별 요약`

- 정비

**메시지**

`도메인이 늘어나도 전체 파이프라인을 다시 만들지 않는다.`

**주석**

- 그래프 DB 의존 없음
- 출처·버전·기준시각 포함
- 현재는 제한된 관계 깊이

### 6쪽. 긴급 설비 판단 예시

**목적**
AI가 추천을 생성하지 않고 선택지별 근거와 제약을 설명한다는 것을 실제 화면 형태로 보여준다.

**레이아웃**

- 좌측 30%: 상황 카드
- 우측 70%: 선택지 비교표

**좌측 상황 카드**

- 설비 A-17
- 상태: 긴급
- 기준시각: 10:00
- 고장 위험 높음
- 생산 진행 중
- 교체 부품 부족
- 품질 검사 보류
- 각 근거 옆에 출처 또는 확인 시각 표시

**우측 비교표**

| 선택지 | 가능한 근거 | 막힌 이유 | 확인 담당 |
|---|---|---|---|
| 지금 멈춤 | 긴급 위험 차단 | 생산 손실 | 공정 |
| 계획정비 | 정비 가능 시간 | 부품 부족 | 정비 |
| 계속운전 | 생산 유지 | 품질 보류 | 품질 |

**표현 규칙**

- 추천 순위처럼 행 전체를 색칠하지 않는다.
- 근거는 파랑, 제약은 빨강, 담당자는 회색 칩으로 표시한다.
- 상단 라벨: `정답 추천이 아닌 선택지별 영향 비교`
- 하단 칩: `근거 노출` `제약 노출` `담당자 연결` `추천 없음`

### 7쪽. 설계 위험을 실패 시나리오로 검증

**목적**
테스트 수가 아니라 설계 위험과 검증 방법의 연결을 보여준다.

**레이아웃**

- 본문 전체: 4개 가로 평가 레인
- 각 레인은 `위험 → 방어 장치 → 장애 주입 → 통과 조건` 순서

| 위험 | 방어 장치 | 장애 주입 | 통과 조건 |
|---|---|---|---|
| 시점 혼합 | 스냅샷 고정 | 오래된 재고·snapshot mismatch | stale 근거 차단 |
| 권한 침범 | 읽기 전용 계약 | 실행 요청 포함 | 작업 생성 0건 |
| 구조 결합 | 어댑터 경계 | 품질·납기 도메인 추가 | 기존 계약 유지 |
| 실패 전파 | 출력 검증·fallback | timeout·깨진 응답·미연결 | 실패 사유 보존 |

**색상**

- 위험: 빨강
- 방어 장치: 파랑
- 장애 주입: 주황
- 통과 조건: 초록

**주의**

- 외부 API fallback은 `장애 격리`의 세부 사례로만 표시한다.
- 평가가 완료되지 않은 항목은 `평가 계획`으로 표시한다.

---

### 8쪽. 신뢰성을 높인 만큼 운영 비용도 측정했다

**목적**
A/B/C 비교를 통해 파이프라인의 이점과 비용을 동시에 보여준다.

**비교군 명칭**

- A: LLM 직접 응답
- B: 근거 패킷 적용
- C: 검증·격리 파이프라인

**레이아웃**

- 2×2 그래프 대시보드
- 각 그래프는 동일한 A/B/C 색상 체계를 사용한다.
- 우측 상단에 `로컬·합성 시나리오 기준` 배지 표시

#### 좌측 상단: 판단 근거 안정성

- 형태: A/B/C 그룹 막대그래프
- 후보 지표: 판단 근거 일치, 시간 정합성, 장애 시 안전 처리
- 서로 다른 산식의 값을 억지로 하나의 백분율로 합치지 않는다.
- 동일한 분모와 루브릭으로 산출된 지표만 한 그래프에 배치한다.

#### 우측 상단: 응답 시간 분포

- 형태: A/B/C 박스플롯
- Y축: 응답 시간(ms 또는 s)
- p50·p95 표시
- 재시도 발생 실행은 주황색 점으로 표시
- 메시지: `검증·재시도·격리의 지연 비용`

#### 좌측 하단: 토큰 사용량

- 형태: 누적 막대그래프
- 계열: 입력 토큰, 출력 토큰, 재시도 토큰
- 금액 단가가 확정되지 않았다면 비용으로 환산하지 않는다.
- 메시지: `근거와 검증 문맥 증가의 사용량 비용`

#### 우측 하단: 안전한 응답 제공 상태

- 형태: A/B/C 100% 누적 막대그래프
- 초록: 정상 응답
- 파랑: 제한된 fallback
- 회색: 안전 종료
- 빨강: 위험한 응답
- 메시지: `엄격한 검증과 판단 지원 가용성의 균형`

**하단 결론**

`C는 위험한 응답을 줄이는 대신 지연과 토큰을 사용하며, fallback은 안전 종료로 인한 가용성 손실을 보완한다.`

**한계 배너**

`현재 결과는 로컬 구현·합성 시나리오 기준이며, 실제 외부 시스템 효과와 운영 KPI는 검증하지 않았다.`

## 4. 8쪽 평가 지표 정의

### 판단 지원 가용성

장애 또는 일부 근거 누락 상황에서도 사용자가 판단에 활용할 수 있는 안전한 결과를 제공한 비율이다. 실제 서버 uptime이나 SLA를 의미하지 않는다.

`판단 지원 가용성 = (정상 응답 + 제한된 fallback) / 전체 평가 요청 × 100`

### 결과 상태 분류

| 상태 | 안정성 | 가용성 | 정의 |
|---|---|---|---|
| 정상 응답 | 성공 | 성공 | 필요한 근거와 시간 조건을 충족한 응답 |
| 제한된 fallback | 성공 | 성공 | 누락·장애·제한을 명시하고 가능한 범위만 제공 |
| 안전 종료 | 성공 | 실패 | 위험한 결과는 막았지만 판단 지원 결과 미제공 |
| 위험한 응답 | 실패 | 성공으로 계산 금지 | 오래되거나 깨진 근거를 정상처럼 제공 |

### 함께 기록할 지표

- 정상 응답률
- 제한된 fallback 비율
- 안전 종료율
- 위험 응답률
- p50/p95 응답 시간
- 평균 입력·출력·재시도 토큰
- 최초 성공률과 재시도 후 성공률

### 평가 시나리오

- 정상 입력
- 외부 호출 시간초과
- 깨진 LLM 응답
- 정비 데이터 누락
- 오래된 재고 데이터
- 스냅샷 불일치
- 일부 운영 도메인 미연결

## 5. 네 가지 트레이드오프

| 트레이드오프 | 확보하는 가치 | 지불하는 비용 | 표현 |
|---|---|---|---|
| 신뢰성 ↔ 응답 시간 | 검증·재시도·장애 격리 | 지연 증가 | A/B/C 박스플롯 |
| 신뢰성 ↔ 토큰 사용량 | 근거·검증 문맥 확대 | 입력·재시도 토큰 증가 | 누적 막대 |
| 엄격한 검증 ↔ 정상 완료율 | 잘못된 출력 차단 | 안전 종료 증가 | 결과 상태 누적 막대 |
| 시간 정합성 ↔ 판단 지원 가용성 | 오래된 근거 차단 | 제공 가능한 답변 감소 | 정상/fallback/종료/위험 비율 |

3번째와 4번째 트레이드오프는 같은 결과 상태 그래프에서 함께 해석한다. 별도 그래프를 추가하지 않는다.

## 6. 부록

### 부록 1. 0.75의 의미

**목적**
0.75를 신규 최적화 결과가 아니라 기존 Canonical V3.1 긴급 상태 경계로 설명한다.

**레이아웃**

- 상단 35%: `0.75`와 해석
- 하단 65%: 상태 구간 막대와 실제 고장 비율 그래프

**상단 문구**

- 신규 최적화값 아님
- 기존 긴급 상태 경계
- 운영 알람 기준 후보
- 관찰 단계 실익 검토

**그래프 1: 상태 구간 막대**

- 정상 0.00~0.20
- 관찰 0.20~0.45
- 주의 0.45~0.75
- 긴급 0.75~1.00
- 0.75 위치에 세로선과 `기존 경계` 표시

**그래프 2: 상태 구간별 실제 고장 비율**

- X축: 정상 / 관찰 / 주의 / 긴급
- Y축: 실제 고장 비율
- 긴급 구간만 강조

**금지 표현**

- 최적 임계값 도출
- 운영 기준 확정

**허용 표현**

- 기존 경계 해석
- 알람 단순화 후보
- 손익분기 관점 검토

**목적**
구현 근거와 미검증 주장을 분리한다.

**레이아웃**

- 좌측: 말할 수 있음
- 우측: 아직 말하면 안 됨
- 중앙 세로 경계선

|---|---|
| 운영 판단 근거 구조 | 실제 비용 절감 |

| 시간 정합성 | 실시간 현장 효과 |
| 책임분리 | LLM 품질 우위 |
| 장애 격리 | 운영 KPI 개선 |
| 로컬 합성 검증 | 실제 서비스 SLA |

**하단 문구**

`구현한 것, 검증한 것, 아직 모르는 것을 분리했다.`

`Backend · AI Integration · Evaluation`

## 7. 데이터 적용 규칙

- 그래프에는 실제 평가 산출물로 계산 가능한 값만 넣는다.
- 평가 완료 전에는 임의 수치나 예시 수치를 넣지 않는다.
- 미완료 항목은 `통합·E2E 평가 예정`으로 명시한다.
- `장애 격리율`, `권한 경계 준수율`처럼 분모가 정의되지 않은 종합 지표를 새로 만들지 않는다.
- 서로 다른 의미의 PASS/FAIL을 임의로 하나의 평균 점수로 합치지 않는다.
- 테스트 개수는 보조 근거이며 발표의 중심 성과로 사용하지 않는다.
- `154 / 0`과 같은 테스트 수치는 최신 실행 결과로 교체하고, 코드 테스트와 LLM 평가 실행을 구분한다.
- 응답 시간은 평균만 표시하지 않고 p50/p95 또는 분포를 표시한다.
- 안전 종료는 안정성 성공이지만 판단 지원 가용성 실패로 계산한다.
- 위험한 응답은 가용성 성공으로 계산하지 않는다.

## 8. HTML 제작 요구사항

- 단일 HTML 파일
- 키보드 좌우 방향키로 한 페이지씩 이동
- 현재 페이지와 전체 페이지 수 표시
- 브라우저 확대·축소와 무관하게 16:9 비율 유지
- 화면보다 클 경우 비율을 유지해 축소
- 인쇄 또는 캡처 시 한 슬라이드가 한 페이지로 출력
- 모든 차트는 SVG로 구현
- 차트 축, 단위, 범례, 표본 수를 명시
- 실제 데이터 주입부는 JavaScript 상수 또는 단일 데이터 객체로 분리
- 값이 없는 그래프는 임의 막대를 그리지 말고 `평가 결과 입력 필요` 상태 표시
- 애니메이션은 사용하지 않거나 페이지 전환 수준으로 제한
- 발표 화면에서 작은 코드 전문을 보여주지 않는다.
