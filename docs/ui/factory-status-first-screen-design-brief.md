# Factory Status First Screen Design Brief

이 문서는 제조 예지보전 workspace의 `공장 현황` 첫 화면과 역할별 강조를 수정할 때 사용하는 화면 기준이다.

## 사용자 문제와 검토 결론

프로젝트는 제조 현장의 흩어진 데이터를 연결하여 사용자가 현재 상황의 맥락을 빠르게 이해하고 역할별 의사결정을 내리도록 돕는다.

첫 화면은 다음 네 질문에 답해야 한다.

1. 지금 어떤 위험이 발생했는가?
2. 왜 먼저 확인해야 하는가?
3. 어떤 대상과 연결되어 있으며, 영향 판단의 근거는 무엇인가?
4. 사용자는 다음에 무엇을 확인해야 하는가?

2026-09-05 검토 결론은 **E. first-screen 정보구조 수정**이다. 기존 5영역은 유지하되 위험 그래프보다 근거·연결 맥락·다음 확인을 먼저 읽게 한다. 엔지니어와 생산관리자를 중심으로 구현하고, 경영진은 공통 운영 위험 overview의 읽기 전용 소비자로 축소한다. 이 문서는 구현 요구사항이며 구현 완료를 의미하지 않는다.

## 참고 범위

- 검토 시 이 문서가 있는 worktree는 `c3f2c482`의 이전 `mvp` 구조이고, backend 대조 기준은 `4efff71f`의 `operations` 구조였다. 구현 시작 전에 대상 checkout과 계약 버전을 고정한다. 다른 checkout의 기능이 이 worktree에도 존재한다고 가정하지 않는다.
- `contracts/schemas/asset-detail-view-model.schema.json`과 함께 실제 목록·상세 API, AI 요약 API, frontend adapter, 선택 상태, 권한, fallback 소비 경로를 확인한다.
- 기존 Operations의 데이터 연결과 navigation을 활용한다. 색상과 카드 배치는 아래 방향으로 조정하되 독립된 데모 화면을 새로 만들지 않는다.
- 스키마 필드의 존재만으로 실제 데이터 공급을 주장하지 않는다. 발표에 사용할 사건의 API 응답과 출처를 확인한다.
- UI는 backend의 계약된 응답을 소비한다. raw JSONL, producer payload, hidden/evaluation truth를 직접 읽거나 누락값을 fixture로 보충하지 않는다.

## 디자인 방향

- 밝은 현장 운영 도구형 UI로 만든다.
- 흰 배경, 밝은 회색 표면, 얇은 경계선, 낮은 채도의 상태색을 사용한다.
- 마케팅 페이지가 아니라 실제 운영 화면처럼 구성한다.
- 첫 화면은 사용자가 지금 어떤 설비를 먼저 봐야 하는지 바로 알 수 있어야 한다.
- 역할은 별도 화면 복제보다 기본 진입과 정보 강조를 바꾸는 컨텍스트로 둔다. 표시 역할을 바꾸는 동작이 실제 권한을 변경해서는 안 된다.

## Persona 범위

| 역할 | 핵심 질문 | 필요한 정보와 판단 | 이번 구현 범위 |
| --- | --- | --- | --- |
| 엔지니어 | 어떤 근거로 이상이며 무엇을 더 확인해야 하는가? | 위험·센서·기여 요인·품질·점검 대상·이력을 확인하고 점검 필요성을 판단 | 공통 상세에서 기술 근거와 부족한 정보를 강조 |
| 생산관리자 | 어떤 운영 판단이 대기 중이며 무엇이 필요한가? | 업무 단계·담당·제약·확인된 운영 맥락을 보고 요청·배정·승인 여부를 판단 | 같은 사건에서 미결 판단과 다음 확인을 강조 |
| 경영진 | 조회 범위 안에서 위험이 어디에 집중되는가? | 상태별 현황과 주요 확인 대상을 읽고 상세 근거로 이동 | 공통 overview 조회로 제한. 독립 KPI·효과 분석 화면은 제외 |

- 엔지니어와 현장 정비 실행자의 권한은 구분한다. 발표 persona를 줄여도 backend의 역할·상태별 권한을 합치지 않는다.
- 경영진의 직접 사용 주기와 생산관리자와 다른 결정은 아직 검증된 요구사항이 아니다.
- 역할별 AI 설명은 같은 근거에서 기술 확인 또는 운영 판단에 필요한 내용을 강조한다. 새로운 위험·영향·담당·작업 상태를 만들지 않는다.

## 첫 화면 레이아웃 기준

`공장 현황` 첫 화면은 아래 5영역 구조를 따른다.

| 위치 | 영역 | 역할 |
| --- | --- | --- |
| 상단 | 3개 핵심 정보 | 현재 문제, 우선 확인 이유, 다음 확인 사항을 가장 먼저 보여준다. |
| 왼쪽 | 상태 맵 / 설비 묶음 | 실제 공급되는 공장·셀·설비 관계와 선택 대상을 보여준다. |
| 가운데 | 선택 사건 맥락과 위험 추세 | 핵심 근거·연결 대상·판단 제한을 먼저 읽게 하고, 위험 추세는 보조 근거로 배치한다. |
| 오른쪽 | 우선 확인 사건 | 확인 우선순위와 관측 시각을 함께 표시한다. 기본 최대 3건과 전체 목록 이동을 제공한다. |
| 하단 | 상세 근거 요약 | 센서·품질·업무 단계·담당 역할·점검 대상을 확인한다. 핵심 근거와 누락 정보는 하단에만 숨기지 않는다. |

- 관측 시각과 갱신 상태는 공통 상태 정보로 표시한다. 관측·처리 시각을 실제 수신 시각으로 바꾸어 부르지 않는다.
- 우선순위는 backend의 유효한 `review_priority`와 그 근거가 있을 때 사용한다. 없으면 기존 계약된 상태·관측 시각 정렬을 사용하고 정렬 기준을 표시한다. 결측을 낮은 위험으로 처리하지 않는다.
- 상태 맵은 실제 공간 배치나 공정 의존성이 확인되지 않으면 공장·셀별 설비 묶음으로 표현한다. 같은 셀에 속한다는 사실을 생산 영향 관계로 확대하지 않는다.
- 위험 이력은 실제 반환된 점만 표시한다. 이력이 부족하면 추세를 합성하지 않는다. 기준선은 backend가 공급한 값만 사용한다.
- 이벤트 목록의 다른 항목을 클릭하면 선택 설비와 사건이 함께 바뀐다. 선택 맵·그래프·근거·AI 요약은 같은 `asset_id`, `event_id`, dataset 및 `snapshot_basis`를 가리켜야 한다.
- 목록 → 사건 상세 → 목록 복귀 시 선택 사건과 조회 범위를 유지한다. 역할 변경 시에도 같은 사건을 유지한다.
- 선택 상태는 테두리, 상태 라벨, 연결 문구로 명확히 드러낸다. snapshot이 일치하지 않는 요약은 현재 설명으로 표시하지 않는다.

## 센서 상태와 데이터 품질

- 항목은 실제 `features[]`에 반환된 값·단위·관측 시각을 기준으로 표시한다. 센서 8종을 고정하지 않으며 가동·수신 상태를 센서값처럼 섞지 않는다.
- 값의 높이·정상 범위·위험색은 공급된 단위와 기준에 근거해야 한다. 서로 다른 센서를 임의의 공통 위험 막대로 환산하지 않는다.
- 값이 실제 갱신될 때만 표시를 갱신한다. 지속 애니메이션이나 임의 변화로 실시간 수신을 연출하지 않는다.
- 데이터 품질과 설비 위험 상태는 구분한다. `unknown`을 수신 대기 또는 정상으로 단정하지 않는다.
- 부족한 값은 `근거 부족`, `확인 필요`로 남긴다. `수신 대기`는 실제 수신 상태 근거가 있을 때만 사용한다.
- 위험 점수는 데이터 품질·관측 시각과 함께 표시한다. 품질 보류와 오래된 데이터 상태를 정상으로 합치지 않는다.

## 한국어·현장용어 매핑

화면의 기본 노출 문구는 현장 사용자가 바로 읽을 수 있는 한국어로 둔다. 시스템 필드명은 필요할 때만 접히는 데이터 매핑 영역에 표시한다.

| 시스템/영문 표현 | 화면 한국어 | 현장 표현 기준 |
| --- | --- | --- |
| asset | 설비 | 자산보다 설비를 우선 사용 |
| asset.display_name | 설비명 | 공급된 이름 사용. 현장 명칭을 임의 생성하지 않음 |
| asset.asset_type | 설비유형 | 현재 계약의 compressor는 압축기, cnc는 CNC 설비 |
| asset.site_id | 공장 | 확인된 이름 매핑이 없으면 ID 유지 |
| asset.cell_id | 공정 셀 / 작업 구역 | 확인된 이름 매핑이 없으면 ID 유지 |
| asset.criticality | 설비 중요도 | low/medium/high는 낮음/중간/높음. null은 미확인, 현재 위험과 구분 |
| risk.current | 위험 점수 | 0–1 원값 또는 일관된 백분율 표시. 예측 시계와 함께 해석 |
| risk.threshold | 기준값 | null이면 기준 미제공. 추가 등급 경계를 임의 생성하지 않음 |
| risk.status_grade | 위험 상태 | normal/attention/warning/critical은 정상/관심/주의/위험으로 각각 구분 |
| data_status.is_data_quality_hold | 데이터 품질 보류 | 위험 등급과 별도로 표시. null 등급을 정상으로 표시하지 않음 |
| features[].current.quality_status | 데이터 품질 | good/bad/unknown은 양호/품질 문제/미확인 |
| operation_context.event_impact.impact_status | 영향 산정 상태 | not_applicable/estimated/withheld_data_quality_hold는 해당 없음/추정/데이터 품질로 산정 보류. 영향 크기와 구분 |
| closed_loop.primary_action.owner_role | 다음 단계 담당 역할 | backend 역할을 표시. 실제 배정 개인과 구분 |
| evidence / evidence_context | 판단 근거 / 연결 맥락 | 출처와 선택된 관계를 표시. 빈 관계를 추론으로 채우지 않음 |
| evidence.gaps | 부족한 근거 | 판단 전 확인해야 할 누락 정보 |
| operation_context.limitations / evidence_context.limitations | 판단 제한 조건 | 각 맥락의 출처·가정·제한을 유지 |
| review_priority.reasons / 별도 decision-support brief의 why_now | 우선 확인 이유 | 서로 다른 계약의 필드임을 구분. 상세 ViewModel에 why_now가 있다고 가정하지 않음 |

## 문구 원칙

- 안전한 갱신 문구를 사용한다: `현재 스냅샷`, `최근 수신`, `주기 갱신`, `갱신 대기`, `근거 부족`, `재평가 대기`.
- `완전한 실시간 관제`, `자동 승인`, `작업지시 자동 생성`, `다운타임 감소 보장`처럼 검증되지 않은 표현은 쓰지 않는다.
- AI 설명은 읽기 전용이어야 한다.
- AI가 위험 상태를 변경하거나 작업지시를 생성하거나 승인하는 것처럼 보이면 안 된다.
- 운전·점검·정비 선택지는 backend가 실제 제공하는 선택지와 조건이 있을 때만 비교 정보로 표시한다. 명령 버튼으로 표현하거나 세 선택지를 고정 생성하지 않는다.
- AI 설명은 저장된 Agent Review Summary 등 별도 계약에서 조회한다. LLM 설명과 deterministic fallback을 구분하고 생성 대기·실패·오래된 요약 상태를 표시한다.
- 위험·수치·우선순위·업무 상태는 각 backend 소유 계약에서 공급한다. AI는 근거와 제약을 설명하며 사실이나 승인 상태를 변경하지 않는다.
- 실제 사람의 요청·승인·실행은 기존 Closed-loop workflow와 backend `available_actions`를 따른다.

## Backend 데이터와 집계 경계

아래는 2026-09-05 코드·계약 검토 기준이다. A는 공급 구현이 있다는 뜻이며 발표 환경의 실제 값까지 검증됐다는 뜻은 아니다. 구현 시작 시 선택 사건의 응답을 다시 확인한다.

| 분류 | 의미 | 적용 항목 |
| --- | --- | --- |
| A | 현재 공급 구현 존재 | 위험·이력·센서·품질, 별도 AI 요약, 조건부 Closed-loop 담당·단계·점검 대상 |
| B | 기존 데이터의 제한된 가공·연결로 가능 | 조회 범위 내 최신 설비 상태 집계, 공장·셀별 묶음, 시각 의미에 맞춘 갱신 표시 |
| C | 필요한 의미 또는 공급 연결이 미구현 | 고정 8종 상태 막대, 복수 등급 기준선, 실제 공간·영향 지도, 반복 이상·미해결 위험, 미연결 relation context |
| D | 현재 확인한 데이터로는 fixture·가정 없이는 표현 불가 | 실측 생산계획·OEE·손실량, ROI·비용절감·다운타임 개선 효과 |

- Product Result/runtime 예측, fixture 기반 운영 맥락·SOP, capacity model 가정, 미확인 정보를 구분한다. Runtime 추론을 했다는 사실이 실제 공장 실측 데이터라는 뜻은 아니다.
- 검토한 runtime context의 OEE·계획 수량·상태별 정지 시간은 고정값 또는 가정에 기반한다. 응답의 `source_type=capacity_model`만으로 실측성을 주장하지 않는다.
- DB에 저장한 fixture나 모델 추정값도 실측 KPI로 승격하지 않는다. 실제 데이터 공급이 확인되지 않으면 본 화면에서 제외하거나 해당 출처를 명확히 표시한 제한된 시연 정보로만 사용한다.
- frontend의 최신 결과 조회 실패 시 local sample을 채우는 경로를 실데이터 성공으로 취급하지 않는다. 오류·부분 응답·fallback은 그대로 드러낸다.
- 경영진 overview는 조회 범위 내 고위험 설비, 상태 분포, 주요 확인 대상, 상세 이동까지만 둔다. 전체 공장을 주장하려면 대상 설비 분모·페이지 coverage·집계 시점·중복 제거 기준이 확인되어야 한다.
- 설비별 최신 상태 집계와 사건 수 집계를 구분한다. 평균 고장확률을 공장 위험도로 부르지 않는다.
- 기존 executive 집계의 ‘decision 기록 없음’을 ‘위험 미해결’로 바꾸어 부르지 않는다. 반복 이상·미해결 상태·생산 영향 순위는 정의와 데이터 연결이 확보될 때까지 제외한다.
- fixture 정지 시간의 단순 합계를 실제 생산 손실로 표시하지 않는다. 현재 상태와 솔루션 도입 효과는 별개이며, 비교 기간·기준선·실측이 없는 개선 KPI는 제외한다.
- API·계약·consumer별 출처를 확인한다. `evidence_context`가 존재해도 빈 값일 수 있으며 별도 운영 decision-support context는 fixture 기반일 수 있다.
- loading, empty, error, partial, stale, permission denied, 품질 보류, AI fallback 상태에서 값을 0·정상·임의 설명으로 대체하지 않는다.

## 발표 전 최소 구현 범위

필수 범위는 **공통 overview 1개와 같은 사건의 상세 화면 1개**다. 상세에서 엔지니어는 기술 근거·점검 대상을, 생산관리자는 미결 판단·업무 단계·다음 확인을 강조한다. 경영진용 페이지를 추가하지 않는다.

5분 시연은 `위험 신호 → 관련 데이터와 ontology context → AI decision-support → 역할별 판단` 순서로 진행한다. 관계나 설명이 미연결이면 이를 숨기지 않고 공급 가능한 근거와 한계를 보여준다.

| 우선순위 | 작업 | 범위 추정 |
| --- | --- | --- |
| 필수 1 | 구현 기준 checkout 고정, 발표 사건 API·snapshot·출처 확인 | 1–2시간 |
| 필수 2 | 기존 overview의 정보 순서·문구·노출 항목 수정 | 2–3시간 |
| 필수 3 | 동일 사건의 근거·AI 요약·역할별 강조 연결 | 2–3시간 |
| 필수 4 | 누락·품질 보류·오래된 요약·fallback·권한 확인과 리허설 | 2–3시간 |

시간은 측정된 일정이나 완료 보장이 아니다. 일요일까지의 목표는 기존 Operations 경로를 활용한 위 범위이며, 데이터·요약 연결이 막히면 지도·집계·비교 카드부터 줄인다.

후순위 또는 제외 범위:

- 경영진 전용 KPI·효과 분석·집계 추세 페이지
- 센서 8종 고정 막대와 실시간 연출 애니메이션
- 실제 배치 근거가 없는 정밀 공장 지도
- persona별 독립 navigation과 화면 복제
- 반복 이상·미해결 위험·생산 손실의 신규 집계
- 정량 선택지 시뮬레이션 확대, 별도 보고서 편집·내보내기, 전체 ontology 탐색기

완료 기준:

1. 위험 신호에서 근거·관련 맥락까지 같은 사건 기준으로 이동한다.
2. AI 설명이 같은 snapshot의 사실·출처·한계를 보존한다.
3. 역할을 바꿔도 사건과 사실은 같고 판단 초점만 달라진다.
4. 데이터 부재·부분 응답·품질 보류·fallback이 정확히 드러난다.
5. 기존 역할별 권한과 Closed-loop workflow가 유지된다.
