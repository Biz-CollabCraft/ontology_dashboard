# 브리핑 생성 개선 검증

## 동작과 적용 범위

AI 설명이 대기·생성·fallback 상태여도 현재 설비 상태와 deterministic 판단 근거를 확인할 수 있다. OpenAI 스키마 변환에서 실제 title/description 필드가 삭제되던 문제를 수정했다.

watcher의 `--generation-policy demand`는 선택 옵션이다. 기본값 always는 유지한다. 일반 위험은 명시 요청까지 보류하고 위험·긴급·임계값 이상과 중요한 변화는 사전 생성한다. 최초 성공 생성 전에는 첫 유효 관측을 별도 비교 기준으로 유지하고, 이후에는 마지막 성공 생성 기준을 사용한다. exact-key 검증과 GET의 생성 금지는 유지한다.

같은 서비스 인스턴스의 설비·범위별 watcher 요청을 직렬화하고, 시작하지 않은 이전 관측 요청을 최신 대기 요청으로 합친다. 실행 중 호출은 취소하지 않고, 명시 요청의 이벤트를 다른 이벤트로 대체하지 않는다. 다중 worker 최신 요청 병합은 포함하지 않는다.

생성 trace에 소요시간, provider 경계 호출 수, 공급자가 보고한 내용 시도/재작성/사용량을 남긴다. 미보고 값은 null이며 provider 호출 수와 HTTP 요청 수는 같지 않다. decision/lookup/completion/failure INFO 로그에는 패킷이나 설명 본문을 기록하지 않는다.

## demand 정책의 한계

DB 결과 기반 부분 맥락 패킷 240건과 별도 통제 fixture에 대해, 지연 3종 × 조회주기 3종 × 실패 유무 × 정책 6종의 216조건을 로컬 재생했다. 공급자 호출·실사용 로그·대기 병합을 재현하는 테스트가 아닌 정책 스케줄러 시뮬레이션이다.

대표 조건은 지연 8초, 조회 15초, 실패 미주입이다.

| 입력 | 정책 | 생성 시작 | 현재 exact 설명 조회 성공률 |
|---|---|---:|---:|
| DB 기반 부분 맥락 | always | 240 | 97.66% |
| DB 기반 부분 맥락 | demand 수정 전 | 31 | 12.98% |
| DB 기반 부분 맥락 | demand 관측 기준 분리 후 | 210 | 85.84% |
| 통제 fixture | always | 56 | 75.00% |
| 통제 fixture | demand | 52 | 70.31% |

DB 재생에는 사용자 명시 생성이 없으며 완전한 운영 맥락도 없다. 따라서 운영 절감률·사용자 대기시간으로 해석할 수 없다. 오래된 설명 반환은 양쪽 0이며 현재 판단 근거 가용성과 AI 설명 가용성은 별개다.

최초 일반 위험 보류 후 기준점이 없어 누적 확률·정비 맥락 변화를 놓치던 문제를 재현하고 수정했다. 유효한 첫 watcher 관측의 복사본을 유지하며 작은 변화마다 덮어쓰지 않는다. 최초 생성 성공 후 이 임시 기준을 제거하고 기존 생성 기준을 사용한다. invalid 입력은 기준점이 될 수 없고, 관측 기준은 캐시 본문 재사용에 사용하지 않는다.

수정 전 demand 36조건과 같은 입력·지연·조회·실패 설정으로 수정 후 demand만 재실행했다. DB 대표 조건의 중요 변화 proxy 요청은 31/218→210/218, 오래된 설명 반환은 0이다. 중요 변화 proxy에는 최초 관측도 포함되므로 실제 위험 변화 누락률과 동일하지 않다. DB 18조건에서 AI 설명 조회 성공률이 모두 개선됐고 통제 fixture 결과는 동일했다. 기존 always의 생성 240회·가용성 97.66%보다는 여전히 낮다. 관측 기준은 프로세스 메모리이며 재시작 시 초기화된다. 따라서 기본 always를 유지한다.

운영 DB 변경·운영 watcher 활성화·배포는 이 변경에 포함하지 않는다. 원본 DB 패킷·응답·로컬 인증정보는 PR에 포함하지 않는다.
