# 라벨 기준과 품질 검증 절차 v1.1 — assistant 일관성 검토안

## 무엇을 평가하는가

현재 범위는 점검 메모의 의미 해석과 읽기 전용 Agent의 추천/보류 경계다. 현장 최적 정비 시점, 설비의 실제 안전성, 사용자 업무 성과를 평가하지 않는다. 실제 점검 데이터 없이 작성한 합성 초안이며, 사람 검수 후에도 별도의 현장 검증이 필요하다.

## 라벨 기준

| 항목 | 정답 판단 기준 |
|---|---|
| record_review | 기존 기록/번호/문서를 조회·비교하라는 명확한 요청. 기록 대상이 있으면 세부 조회 절차가 없어도 모호하다고 단정하지 않는다. |
| new_measurement | 새 물리 측정값이나 진단 시험을 얻으라는 명확한 요청. 단순히 확인하라는 말은 포함하지 않는다. |
| ambiguous_request | 현재 지시의 대상 또는 요청 종류를 원문/제공 문맥에서 특정할 수 없다. |
| ambiguous_other | 요청 외의 현재 문장 의미가 특정되지 않는다. 위험 판단이 어렵다는 것과 문장 뜻이 모호한 것은 다르다. |
| clear_other | 명확한 사실, 정보 누락 보고, 해결된 모호함, 취소된 요청, 선택 사항 등. 명확한 근거 충돌도 문장 의미 자체는 clear_other일 수 있다. |
| information_missing | 필요한 기록/값이 없거나 확인되지 않았다고 명시한다. 불분명한 지시어 자체와 구별한다. |
| unresolved_conflict | 같은 대상·시점·조건에 대한 서로 양립하지 않는 근거/판단이 현재 해소되지 않았다. 시간 충돌·재고 부족·모호한 지시만으로 true로 만들지 않는다. |
| uncertain | 뜻을 특정할 수 없다. 단순한 자료 누락만으로 true가 되지는 않는다. |
| measurement_status | required / not_required / optional / not_stated / unclear. 조건부 요구처럼 현재 범주로 정답을 합의하기 어려우면 미정으로 남긴다. |
| measurement_required | 현재 문맥에 명시된 새 측정의 필수 요구. 선택/취소/기록 조회/단순 누락은 false다. |

원문에 여러 내용이 있으면 서로 배타적인 하나로 줄이지 않는다. 충돌과 재측정 요구, 자료 누락과 의미 불명확함은 동시에 참일 수 있다. 지시가 뒤에서 명확해지거나 철회됐다면 현재 유효한 의미를 기준으로 한다. 도메인 판단이 필요한 사례는 모델 출력에 맞춰 정답을 정하지 않는다.

## 두 항목의 경계와 적용 순서

information_missing는 **원문에 명시된 기록/값의 부재 또는 미확인**을 뜻한다. true에는 누락·미기재·미확인 대상과 그 원문 근거가 있어야 한다. false는 실제 정보가 완전하다는 보증이 아니라 이 문장에서 누락을 확인하지 못했다는 뜻이다.

- 새 측정 요청만 있으면 기존 값의 누락을 추론하지 않는다. 재측정은 기존 값이 있어도 요청할 수 있다.
- 서로 반대인 두 판단이 있으면 unresolved_conflict로 표현한다. 기록 누락 진술이 함께 없다면 information_missing는 false다.
- 기존 기록을 검토하라는 요청만으로 그 기록이 없거나 미확인이라고 추론하지 않는다.
- 무엇을 하라는지 모르는 지시어는 의미의 모호함이다. 그 자체를 기록/측정값 누락으로 바꾸지 않는다.

measurement_status는 **현재 유효한 새 측정 요청의 상태**이며, 측정값의 존재 여부와는 별개다. 먼저 정정·철회·조건을 읽고 다음 기준을 적용한다.

| 현재 원문의 상태 | 라벨 |
|---|---|
| 새 물리 측정/시험을 반드시 수행하라고 명시 | required |
| 새 측정을 선택·교육·참고용으로 제안하며 필수는 아니라고 명시 | optional |
| 새 측정을 철회·불필요로 명시하거나 기록 검토로 대체했다고 정정 | not_required |
| 현재 지시의 대상/작업 종류가 특정되지 않아 측정 요청인지도 판정할 수 없음 | unclear |
| 지시/진술을 이해할 수 있지만 새 측정에 대한 언급이 없음 | not_stated |

선택 사항에 '필수는 아니다'가 함께 있으면 optional이다. 이는 추가 측정을 취소한 not_required와 다르다. 기록 검토만 명시하면 not_stated지만, 새 측정 대신 기록을 보라고 정정하면 not_required다. unclear는 새 측정을 하라는 뜻이 아니므로 measurement_required를 true로 바꾸지 않는다. 다른 문장의 명시적이고 독립적인 측정 요구가 있으면 그 요구도 함께 읽는다. 조건 성립 여부를 모르는 요청 4건은 계속 unresolved로 둔다.

이 검토는 v1 모델 출력을 본 뒤 수행한 assistant 검토다. 사람의 독립 검수나 정답 확정으로 기록하지 않는다. 수정 세트는 개발/회귀 용도로 취급하며 향후 독립 평가에는 새 원문을 사용한다.

## 행동 정답과 정책의 분리

- `policy_allowed_actions`는 고정 배경에서 서버 정책이 허용하는 범위다. 가장 좋은 행동의 정답이 아니다.
- 의미 확인/근거 조정이 필요한 문구는 선행 확인 보류가 필요하다는 제약을 제안한다.
- 명시적 측정 요구는 정책이 허용하는 경우 진단 보강 제약을 제안한다.
- 이외 문구만으로 MONITOR/REQUEST_INSPECTION/정비 두 행동의 우선순위를 정하지 않는다. `exact_action_ranking_scored=false`다.
- 정비 action 순위를 평가하려면 위험 추세, 실제 점검 결과, 일정/부품 문맥을 추가하고 사람이 허용 답 집합과 선호 답을 따로 검수한 별도 골드셋이 필요하다.

## 검수와 확정

1. 개발·평가를 family 단위로 분리하고 유사한 문장 변형이 양쪽에 없는지 검수한다. 자동 검사는 동일 문장과 family 분할만 확인하므로 의미상 유사성을 보증하지 않는다.
2. 검수자는 먼저 원문으로 라벨/근거를 작성한다. 가능하면 도메인 담당자와 두 번째 검수자가 독립적으로 작성하고 차이를 조정한다. 한 명만 검수했다면 한 명 검수임을 기록한다. assistant의 초안을 독립 검수로 세지 않는다.
3. 각 라벨의 일치/불일치와 의견을 기록한다. 합의가 안 된 사례는 unresolved이며 점수 분모에 넣지 않는다. 그렇다고 조용히 삭제하지 않고 제외 수와 사유를 공개한다. 현재 export는 모든 사례가 해결·검수되어야 성공하므로 제외할 경우 제외 기록과 함께 새 데이터셋 버전을 만들어야 한다.
4. 원문·배경·라벨·행동 제약이 확정되면 사례 내용 hash에 검수자를 연결한다. 원문/정답 변경은 재검수가 필요하다. 전체 모델 프롬프트·schema·모델 ID·추론 설정·입력·정답 hash를 함께 고정한다.

## 모델 품질 평가 — 검수 이후 실행

- 비교 모델: gpt-4o-mini와 gpt-5.6-luna. 요청 모델과 API가 반환한 모델을 모두 기록한다. 설정 파일의 기본 모델을 암묵적으로 사용하지 않는다.
- 최종 평가용 문장은 개발/프롬프트 수정에 쓰지 않는다. 같은 입력·schema로 모델별 순서를 교대하며 3회 반복한다. 반복은 독립 사례 수로 세지 않는다.
- 주요 지표: 라벨별 오탐/누락, 필요한 확인 누락, 불필요 보류, 측정 요구 오탐/누락. 단일 action 우선순위 정확도는 이 데이터셋에서 계산하지 않는다.
- 처리 오류, 응답 모델 불일치, 근거 ID/인용 검증 오류, fallback은 별도 실패다. 실패를 올바른 보류로 세지 않는다. 분류 지표의 유효 응답 분모와 전체 입력 수를 모두 표시한다.
- 추론 출력과 실제 LangGraph 경로 재생 결과는 구분한다. 현장 화면/API를 통하지 않은 replay를 live backend 성능으로 표현하지 않는다.
- 전체 점수뿐 아니라 family·언어·사례별 결과와 알려진 회귀 사례를 함께 본다. 단독 입력과 batch 입력을 구분한다. 토큰 및 API 지연은 batch 단위로 기록하고 화면 지연으로 환산하지 않는다.

## 통과 판단

코드 경계는 정책 밖 행동·도메인 mutation·출처 위조 수용이 0이어야 한다. 코드 테스트 통과만으로 모델 품질 통과를 선언하지 않는다.

모델 품질은 골드 검수 이후, 결과를 보기 전에 허용 가능한 오탐/누락 기준과 중요한 사례를 담당자와 정한다. 기존 결과에 맞춰 합격선을 사후 조정하지 않는다. 기존 회귀의 개선/악화와 남은 한계를 함께 기록한다. 현재는 도메인 검수와 품질 합격선이 확정되지 않았으므로 '품질 인증 통과' 상태를 만들지 않는다.

마지막 실제 사용 흐름 검증은 별도다. 원문·출처 표시, 보류 사유의 비단정적 표현, 사람이 원문을 확인할 수 있는지, 승인 전 실제 작업이 실행되지 않는지를 화면→API에서 확인한다. 현재 프론트는 다른 작업 중이므로 이 단계는 수행하지 않는다.
